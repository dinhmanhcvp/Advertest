# AdverTest: Enterprise Data & Orchestration Specification

## 1. Architectural Philosophy: The Synthesizing ELT Pipeline
While AdverTest functions as a computer vision robustness framework, structurally it is designed as a **Specialized ELT (Extract, Load, Transform) Pipeline** for synthetic PII edge cases. 

Instead of traditional tabular data, AdverTest processes unstructured tensor data (images/video frames). The pipeline adheres strictly to Data Engineering best practices:
- **Extract (Triage):** Ingests raw frames from the central data lake, running lightweight baseline inference to extract only "Hard Negatives" (IoU < 0.5).
- **Load (Storage):** Loads these highly informative, isolated samples into a staging buffer (Object Storage) rather than keeping them in ephemeral GPU VRAM.
- **Transform (Attack Engine):** Applies non-destructive, physics-based transformations (blur, noise, distortion) via Albumentations to generate adversarial curricula.

## 2. Data Governance, Lineage, and Storage
Data integrity and tracability are paramount, especially when handling PII-adjacent synthetic data.

### 2.1 Ingestion via Presigned URLs (Data Block)
To ensure compliance and avoid massive data egress costs, AdverTest does not pull entire datasets locally. It integrates with the enterprise "Data Block" (Centralized Storage) via **Presigned URLs**.
1. The orchestrator requests a batch of presigned URLs for validation data.
2. The Triage workers stream the data directly into memory, infer, and drop the memory block immediately if the IoU is acceptable.
3. Only the subset of failed samples is forwarded to the staging environment.

### 2.2 Strict Data Lineage (`audit_trail.json`)
Every synthetic image generated by the Attack Engine is accompanied by an immutable metadata record in `audit_trail.json`. This serves as strict **Data Lineage**, answering:
- *What was the source frame?* (Original URI)
- *Why was it transformed?* (VLM Insight: e.g., "Motion Blur detected")
- *Exactly what transformations were applied?* (The JSONB `applied_chain` array, e.g., `["OpticalDistortion(severity=3)"]`)
- *Who/What initiated it?* (Job ID and RL Policy Version)

This lineage is persisted in a PostgreSQL `JSONB` column, ensuring data engineers can run complex analytical queries (e.g., `SELECT * FROM attack_pool WHERE applied_chain @> '[{"type": "MotionBlur"}]'`) directly on the metadata.

## 3. Taxonomy Standardization
To integrate seamlessly with the Enterprise's central metadata registry, AdverTest enforces a strict taxonomy for model failure modes.
- Unstructured VLM text outputs are parsed and mapped to a predefined schema (e.g., `ERROR_BLUR_MOTION`, `ERROR_OCCLUSION_PARTIAL`, `ERROR_SENSOR_NOISE`).
- This standardization allows the Data Platform team to build automated dashboards correlating model drift in production directly back to specific physical phenomena categorized during the AdverTest QA phase.

## 4. Scalability and Event-Driven Readiness
The current implementation utilizes FastAPI and Celery/Ray for orchestrated polling and task execution. However, the architecture is decoupled to support true Event-Driven Architecture (EDA) for enterprise scale.

- **Kafka / Redpanda Integration:** The FastAPI gateway acts as a facade. The underlying queue can trivially be swapped to Apache Kafka.
- **Real-Time Video Ingestion:** Instead of batch processing a static dataset, the Triage workers can subscribe to a Kafka topic (e.g., `telemetry.cameras.raw_frames`), process them on the fly, and publish Hard Negatives to a `mlops.advertest.failed_frames` topic.
- **Consumer Groups:** The Attack Engine acts as a consumer group, dynamically scaling up GPU pods (via Kubernetes/KEDA) based on the lag in the `failed_frames` topic.
